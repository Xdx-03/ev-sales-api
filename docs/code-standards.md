# Python 自动化测试代码规范

## 1. 目标与适用范围

本规范适用于仓库内的 Python 业务用例、API 封装、HTTP 客户端、配置、报告和执行入口。目标按优先级排列：

1. 读者能够从测试名称和步骤直接理解业务行为。
2. 修改接口路径、认证或分页参数时，改动集中且容易定位。
3. 用例可独立、可重复执行，失败信息足以定位问题。
4. 格式与常见代码问题由工具检查，不依赖个人习惯。

规则分为“必须、应该、可选”。违反“必须”规则时，提交不能合并；临时豁免方式见第 10 节。

## 2. 分层与职责

| 层级 | 当前目录/文件 | 允许的职责 | 禁止的职责 |
| --- | --- | --- | --- |
| 配置层 | `config/`、`ev_api/config.py` | 配置模板、环境变量覆盖和类型转换 | 写死真实账号或生产地址 |
| 测试上下文层 | `tests/conftest.py` | fixture、环境预检、登录客户端和写数据门禁 | 编写具体业务断言 |
| HTTP 客户端层 | `ev_api/client.py` | HTTP 会话、JWT、超时、传输安全和请求证据 | 感知订单、试驾等业务规则 |
| 领域 API 层 | `ev_api/apis/` | 按领域封装鉴权、目录、订单、试驾、售后和 AI 操作 | 写测试断言、读取环境变量、管理报告目录 |
| 测试场景与断言层 | `tests/test_*.py`、`ev_api/assertions.py` | 描述场景、调用业务方法、断言业务结果 | 重复实现认证、超时、脱敏或复杂请求拼装 |
| 执行与报告层 | `run_api_tests.py`、CI 配置 | 参数透传、报告、通知和退出码 | 改写测试结果或隐藏失败 |

必须：业务接口通过对应领域 API 类访问。跨模块权限探测和客户端本身的行为验证可以直接调用 `ApiClient`，但不得复制客户端已有的超时、传输安全和日志逻辑。

`preflight.py`、`redaction.py` 提供横切安全能力；Ruff、pytest marker、GitHub Actions 和 Jenkins 提供横切质量治理，不重复计入主架构层数。

## 3. Python 基础规范

### 必须

- 使用 Python 3.11 及以上版本、UTF-8、LF 换行、4 空格缩进。
- 每行最多 100 个字符；由 Ruff formatter 统一换行和引号。
- 导入顺序为标准库、第三方库、本项目模块，组间空一行。
- 禁止一行定义函数、类或多个语句，禁止分号拼接语句。
- 公共类和非显而易见的辅助函数必须有简短 docstring，说明“为什么存在”或业务语义。
- `ev_api/` 中的公共方法必须声明参数和返回类型；测试函数统一返回 `None` 的语义，不返回业务数据。
- 禁止裸 `except:`、静默吞异常和无边界重试。捕获异常时应缩小异常类型并保留可理解的错误上下文。
- 代码提交前必须通过：

  ```bash
  python -m ruff format --check .
  python -m ruff check .
  ```

### 应该

- 函数控制在一个清晰职责内；需要多个“并且”才能描述时，拆成命名明确的辅助函数。
- 优先提前返回，减少深层嵌套。
- 业务含义不明显的数字或字符串提取为常量或有名字的配置项。
- 注释解释设计原因、风险或约束，不重复翻译代码本身。

### 可选

- 对复杂响应结构增加 `TypedDict`、数据类或协议类型；简单 JSON 场景无需为了类型而过度包装。

## 4. 命名规范

### 必须

- 文件、函数、fixture、变量使用 `snake_case`。
- 类使用 `CapWords`，缩写按单词处理，例如 `ApiClient`、`OrderApi`，不使用 `APIClient`。
- 常量使用 `UPPER_SNAKE_CASE`，内部常量以 `_` 开头。
- 测试名称使用 `test_<功能>_<场景>_<预期>`，名称必须能回答“测什么、什么条件、期望什么”。
- 业务 API 方法使用明确动词和对象，例如 `create_order()`、`list_my_orders()`、`submit_feedback()`；禁止新增含义模糊的 `create()`、`list()`、`handle()`。
- 领域模块使用 `<domain>_api.py`，一个文件只维护一个功能领域；禁止重新创建集中所有端点的 `business_api.py`。
- 布尔变量使用 `is_`、`has_`、`can_` 或 `should_` 前缀。

示例：

```python
def test_pay_nonexistent_order_returns_404(...):
    response = order_api.pay_order(missing_order_id)
    assert_json_code(response, expected=404)
```

## 5. 测试用例规范

### 必须

- 一个测试验证一个可识别的业务行为。必要的“创建 → 操作 → 回查”可以作为一个闭环，但不混入无关断言。
- 用例按“准备、执行、断言”组织；步骤较多时使用有业务含义的 Allure `step`。
- 同时验证业务码和关键业务结果。只断言 HTTP 200、字段存在或列表非空不能作为完整业务断言。
- 同一规则的多组输入使用 `pytest.mark.parametrize`，禁止在测试函数内用循环隐藏独立失败。
- 用例不得依赖文件顺序、测试函数顺序或上一次运行残留的数据。
- 参数化写入场景必须为每个参数准备独立业务记录，前一个参数修改过的数据不得作为后一个参数的前置条件。
- 禁止 `time.sleep()`。需要等待时轮询可观测状态，并设置最大时长与失败信息。
- 预计创建或修改业务数据的用例必须标记 `destructive`，并由 `--run-destructive` 显式开启。
- 已选择的执行集中，缺少必需配置或出现跳过场景必须使执行失败，不能生成不完整的绿色结果。

### 应该

- 失败信息描述预期、实际结果和脱敏后的最小上下文。
- 参数名、Allure 标题和测试名称使用同一业务词汇。
- 对可清理数据在 fixture 终结阶段清理；无删除接口时只允许在可重置的专用环境运行并记录限制。

## 6. 标记与执行分层

| 标记 | 含义 | 使用规则 |
| --- | --- | --- |
| `api` | 黑盒 API 场景 | 所有调用被测 REST API 的测试必须包含 |
| `regression` | 回归套件 | 稳定且具有持续回归价值的场景必须包含 |
| `smoke` | 快速冒烟 | 环境可用性和最核心公开接口 |
| `critical` | 发布阻断 | 鉴权、权限、订单等高业务风险场景 |
| `slow` | 慢场景 | 依赖 AI 或其他耗时外部服务 |
| `destructive` | 业务写入 | 创建或修改业务数据，默认禁用 |
| `ui` | UI 场景预留 | 当前仓库不包含 UI 测试 |

新增 marker 必须先在 `pytest.ini` 注册，并在测试策略中说明选择器和执行条件。

## 7. API、配置与数据

### 必须

- 基地址、会话、超时、请求日志和传输错误只在 `ApiClient` 中处理；登录契约由 `AuthApi` 维护。
- 每个网络请求必须有显式超时；业务用例不得绕过统一客户端直接调用 `requests`。
- 业务 API 方法接收 Python 风格参数，在封装内部转换为服务端字段，例如 `page_number` → `pageNum`。
- 凭据只通过未跟踪配置、环境变量或 CI 凭据服务注入。
- 业务数据必须通过类型化 `BusinessData` 读取，禁止在测试中重新使用无类型字典键访问。
- 每次执行必须使用唯一运行 ID；所有请求携带 `X-Test-Run-Id`，支持自由文本的写入数据使用相同 ID 标记。
- 禁止连接生产环境，禁止使用真实客户资料，禁止提交本地报告、数据库备份和访问令牌。

### 应该

- 新增接口前先放入对应领域 API；只有业务职责明显不同才创建新模块和类。
- 对后端支持删除的资源增加 fixture 清理；暂时无法删除的数据必须只在可重置环境创建。
- 环境变量名称统一使用 `EV_` 前缀。

## 8. 断言、日志与报告

### 必须

- 通用响应结构使用 `ev_api.assertions`，避免每个测试重复解析业务码。
- 请求、响应、异常或报告地址进入 Allure/CI 前必须经过脱敏边界。
- 失败不得被 `skip`、通知异常或旧报告覆盖；零通过用例必须返回失败。
- 日志和断言信息不得输出密码、JWT、Cookie、手机号、地址、VIN、订单号等真实数据。

### 应该

- 报告记录必要的请求摘要、响应状态和业务步骤，不附加与定位无关的大段数据。
- 对业务副作用通过公开 API 回查，保持测试对被测系统内部实现无感知。

## 9. 自动质量门禁

提交和 Pull Request 必须依次通过：

1. `python -m ruff format --check .`
2. `python -m ruff check .`
3. `python -m compileall -q ev_api tests run_api_tests.py`
4. `python -m pytest --collect-only -q`
5. `python -m pytest --collect-only -q -m "not destructive and not database"`

GitHub Actions 只证明代码质量和用例可收集。真实 API 结果必须由连接专用测试环境的 Jenkins 或人工任务产生。

## 10. 例外与治理

- 临时豁免必须在 Issue 或 Pull Request 中记录：规则、文件/用例、原因、负责人和到期时间。
- Ruff 规则只能在最小代码行或文件范围内忽略，并写明原因；禁止整仓关闭规则来迁就单个问题。
- 不稳定用例必须标记、隔离和修复，禁止无限重试、永久跳过或删除失败证据。
- 每次修改本规范时，同时更新自动检查配置，避免“文档要求”和“实际门禁”不一致。
