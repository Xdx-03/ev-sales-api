## 3. 缺陷记录

### API-AUTHZ-001 客户越权访问返回系统异常而非 403

在线跟踪：[GitHub Issue #1](https://github.com/Xdx-03/ev-sales-api/issues/1)

| 字段 | 内容 |
| --- | --- |
| 状态 | 待修复 |
| 严重程度 | S2（高） |
| 优先级 | P1 |
| 所属模块 | 权限控制 / 全局异常处理 |
| 复现情况 | pytest 与 Newman 均稳定复现 |
| 关联用例 | `test_customer_access_to_system_user_list_is_forbidden` |

前置条件：使用已启用的普通客户测试账号登录，并携带有效 JWT。

复现步骤：

1. 调用登录接口获取普通客户 Token；
2. 在 `Authorization: Bearer <token>` 请求头中携带 Token；
3. 请求 `GET /sys/user/list`；
4. 检查 HTTP 状态和业务响应码。

预期结果：服务端拒绝访问，返回 HTTP 403，业务码为 403，不返回后台用户数据。

实际结果：服务端返回 HTTP 200，业务码为 500，提示“系统异常，请重试”。未观察到后台用户数据泄露。

服务端证据：日志记录 `AuthorizationDeniedException: Access Denied`，随后被 `GlobalExceptionHandler` 记为“运行时未知异常”。这表明权限判断本身已拒绝请求，但异常映射错误地把权限异常转换成通用 500 响应。

影响：

- 前端和调用方无法区分权限不足与服务端故障；
- 监控会把正常的权限拒绝统计为系统异常；
- HTTP 200 与业务失败语义冲突，影响网关、告警和客户端重试策略；
- 关键权限回归质量门禁无法通过。

建议：为 `AuthorizationDeniedException` 或 `AccessDeniedException` 增加明确的 403 异常映射，并统一 HTTP 状态与业务码。修复后重新执行非破坏性回归。

### API-ORDER-001 订单交付后库存锁定订单未释放

在线跟踪：[GitHub Issue #2](https://github.com/Xdx-03/ev-sales-api/issues/2)

订单、两类支付流水、库存销售状态和交付单都已正确更新，但交付后库存记录的 `lock_order_id` 仍非空。只读 SQL 复核结果为 `order_status=70`、`payments=2`、`inventory_status=40`、`lock_released=0`、`delivery_status=30`。

从实现推断，`setLockOrderId(null)` 后调用 `updateById` 可能被 MyBatis-Plus 默认非空更新策略忽略。该推断需要开发确认，自动化断言保持不变。

### API-TD-RATING-001 试驾反馈接受评分 0 的非法值

在线跟踪：[GitHub Issue #3](https://github.com/Xdx-03/ev-sales-api/issues/3)

评分 0 请求返回 HTTP 200、业务码 200，与约定的 1–5 范围不符。评分 6 的旧结果因复用已被修改的预约而不作为缺陷证据。实现中未观察到评分范围校验，数据库表也没有相应 CHECK 约束；这会污染满意度统计和客户标签数据。评分 6 必须使用另一条未评价预约独立复测。

## 4. 框架修正记录

本轮首次执行时，已认证客户端采用 session 级生命周期。被测系统启用了“新登录使旧 Token 失效”，后续用例因此复用失效 Token，出现 4 个 401，并让一个越权用例产生假阳性。

框架已将客户和管理员认证客户端调整为用例级生命周期，每个场景独立登录。修正后客户订单、试驾、售后和个人资料查询均恢复通过，越权用例稳定暴露 `API-AUTHZ-001`。

Windows 本地执行曾因 Python 默认 GBK 与终端 UTF-8 不一致导致中文失败信息乱码。统一入口现会把自身和 pytest 子进程输出固定为 UTF-8；修正后的同范围回归已确认测试标题、响应消息和汇总均可读。
