# 自动化覆盖矩阵

## 1. 场景统计

统计口径为 pytest 参数化后的收集项，不以测试函数数量代替场景数量。

下表仅统计 `tests/` 的业务场景。`framework_checks/` 中的合成框架检查由独立命令与 CI 步骤执行，不加入业务规模或业务通过率。

| 用例模块 | 收集场景 | 默认安全回归 | 写数据场景 | 主要覆盖 |
| --- | ---: | ---: | ---: | --- |
| `test_catalog.py` | 5 | 5 | 0 | 公开列表、库存结构 |
| `test_authentication.py` | 2 | 2 | 0 | 无效凭据、客户登录 |
| `test_permissions.py` | 5 | 5 | 0 | 匿名拦截、客户越权拦截 |
| `test_customer_queries.py` | 4 | 4 | 0 | 客户订单/试驾/工单列表、资料 |
| `test_test_drive.py` | 3 | 0 | 3 | 创建、重复冲突、非法评分 |
| `test_orders.py` | 2 | 0 | 2 | 下单/定金/配车/尾款/交付、不存在订单 |
| `test_after_sales.py` | 1 | 0 | 1 | 创建工单并回查 |
| `test_ai_shopping_guide.py` | 4 | 3 | 1 | 鉴权、边界、回复与历史 |
| `test_database_consistency.py` | 1 | 0 | 0 | 客户资料 API-DB 状态一致性 |
| **合计** | **27** | **19** | **7** | 26 个黑盒 API + 1 个只读数据库校验 |

> 同一个场景只计入一个执行层。默认安全回归排除 `destructive` 和 `database`；两类场景均需显式开启。

Postman/Apifox 集合包含 12 个安全请求，覆盖登录、公开目录、客户本人查询和权限边界。它用于手工调试和跨工具复核，不重复计入上述 27 个 pytest 场景。

## 2. 需求与用例映射

| 需求 ID | 风险/需求 | 自动化验证 | 标记 | 前置条件 |
| --- | --- | --- | --- | --- |
| API-PUB-01 | 基础公开数据不可用会阻断用户浏览 | 品牌、车型、SKU、文章列表可访问且返回预期数据类型 | `smoke` | 服务可达 |
| API-PUB-02 | 可售库存结构异常会影响下单选择 | 校验 `count`、`hasInventory` 类型及两者逻辑一致性 | `smoke` | 基础库存数据 |
| API-AUTH-01 | 无效登录凭据被接受 | 不存在账号与错误密码组合返回 401 | `auth` | 服务可达 |
| API-AUTH-02 | 登录成功但未返回令牌 | 客户登录返回非空令牌 | `auth` | 有效客户账号 |
| API-RBAC-01 | 未登录用户访问客户资源 | 四类受保护接口拒绝匿名请求 | `permission` | 服务可达 |
| API-RBAC-02 | 客户访问后台用户列表 | 客户令牌被后台接口拒绝 | `permission` | 有效客户账号 |
| API-CUS-01 | 客户业务列表契约漂移 | 订单、试驾、工单列表返回分页/列表结构 | `business` | 有效客户账号 |
| API-CUS-02 | 客户资料接口契约漂移 | 个人资料返回对象结构 | `business` | 有效客户账号 |
| API-DB-01 | API 返回状态与数据库记录不一致 | 比较客户资料的 ID、删除标记、阶段和意向等级 | `database` | 隔离环境；SELECT-only 数据库账号 |
| API-TD-01 | 重复预约被错误接受 | 创建预约后再次提交相同车型/日期，并复核冲突查询与列表 | `business, destructive` | 可预约 `model_id` 和未来时段 |
| API-TD-02 | 非法评分绕过校验 | 对两个独立的已完成预约分别提交评分 0 和 6，预期业务码 400 | `business, boundary, destructive` | 客户本人两条不同的已完成且未评价预约 ID |
| API-ORD-01 | 订单状态或跨模块副作用异常 | 客户创建订单；管理员完成定金、配车、尾款和交付；回查订单、支付流水、库存与交付单 | `business, destructive` | 可售 `sku_id`、匹配的在库车辆、客户/管理员账号、可重置环境 |
| API-ORD-02 | 不存在订单被支付 | 不存在订单返回 404 语义 | `business, destructive` | 有效客户账号 |
| API-AS-01 | 售后工单创建后不可查询 | 创建工单并在客户列表中回查 | `business, destructive` | 有效客户账号；环境需要时提供合成 VIN |
| API-AI-01 | AI 接口绕过鉴权或接受空输入 | 匿名请求和空消息被拒绝 | `ai, permission/boundary` | AI 路由可达 |
| API-AI-02 | 无效/降级回复误判成功或对话无法回查 | 校验回复对象、文本与已确认降级提示，按会话 ID 检查历史一致性 | `ai, business, destructive` | AI 服务可用；不涉及事实性或推荐质量评分 |

## 3. 写数据场景执行状态

7 个写数据场景中，售后建单、试驾重复预约和不存在订单支付通过；订单交付因库存锁未释放失败；评分 0 确认因接口接受非法值失败；评分 6 的旧执行共用了已被评分 0 修改的预约，证据无效，待用独立预约重跑；AI 会话因 Ollama 不可用而环境阻塞。失败、阻塞和无效证据均不计为通过。

## 4. 当前主要缺口

以下内容尚未自动化，因此不在对外成果中宣称已覆盖：

- 订单取消后的库存释放；
- 重复下单的稳定业务错误码和数据唯一性；
- 管理员分配售后技师、耗材登记、完工计价及客户评价防重复；
- 客户之间的订单、试驾和工单数据隔离；
- 退出登录后的令牌失效；
- 支付流水只读性和完整审计日志；
- UI、性能、安全渗透及真实第三方支付链路。

## 5. 统计复核命令

```bash
python -m pytest --collect-only -q
python -m pytest --collect-only -q -m "not destructive and not database"
python -m pytest --collect-only -q -m destructive
python -m pytest --collect-only -q -m database
```

每次增删用例后，应以命令输出更新本文件，避免文档数字与代码漂移。
